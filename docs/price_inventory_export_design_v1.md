# Price / Inventory / Channel Export Design v1

작성일: 2026-05-16

## 1. 목적

이 문서는 상품관리 모듈의 다음 확장 대상인 가격, 재고, 판매처별 export 기능을 어떤 구조로 설계할지 정리한다.

지금 설계를 먼저 하는 이유는 가격과 재고가 여러 판매처 업로드 양식에 직접 연결되기 때문이다. 먼저 기준 SKU, 판매처 코드, 가격, 재고, 내보내기 이력을 어떤 단위로 분리할지 정리해 두어야 이후 DB 초안, API, 프론트 화면, CSV/XLSX 생성 기능을 서로 섞지 않고 확장할 수 있다.

이번 작업은 운영 DB 반영보다 문서 설계가 우선이다. 실제 DB에 반영할 구조를 바로 만들거나 적용하지 않고, 후보 테이블과 처리 흐름만 문서로 정리한다. 따라서 운영 Supabase, NAS PostgreSQL, 로컬 DB를 건드리지 않는 안전한 선행 작업이다.

이번 문서에는 실제 테이블 생성문, 적용 SQL, 실행 절차를 포함하지 않는다.

## 2. 현재 구조와 유지해야 할 원칙

현재 상품관리 v1은 read-only 검수 화면 중심이다. API는 `product_code` 영역의 상품, SKU, alias, channel mapping, product image 정보를 조회하고, 프론트는 이를 기준으로 SKU 목록, SKU 상세, alias 검색, 변경 요청 placeholder를 보여준다.

| 기존 구조 | 역할 |
|---|---|
| `product_master` | 상품 단위의 기준 정보. 상품명, 내부 상품 기준, 상품 단위 코드 연결의 기준이 된다. |
| `sku_master` | 옵션/SKU 단위의 기준 정보. 가격, 재고, 판매처 SKU 연결의 중심 키가 된다. |
| `code_alias` | 셀피아 SKU, 셀피아 상품코드, 자사코드, Smartstore 옵션번호 후보 등 여러 코드 체계를 내부 상품/SKU에 연결한다. |
| `sku_channel_mapping` | MakeShop, Smartstore 등 판매처의 상품코드/옵션코드/SKU 코드를 내부 SKU와 연결한다. |
| `product_image` | SKU별 대표 이미지와 이미지 URL을 관리한다. export에서 이미지 URL이 필요한 판매처의 입력값 후보가 된다. |

유지해야 할 원칙은 다음과 같다.

- 셀피아 SKU 또는 VSKU를 내부 기준으로 유지한다.
- Smartstore, MakeShop, Ably, PlayAuto 등 판매처 코드는 alias 또는 channel mapping으로 연결한다.
- 후보 코드와 확정 코드는 분리한다. 예를 들어 Smartstore 후보 옵션번호는 확정 옵션번호처럼 export에 바로 사용하지 않는다.
- 기존 `product_master`, `sku_master`, `code_alias`, `sku_channel_mapping`, `product_image` 구조를 깨지 않고 확장한다.
- 가격, 재고, export 기능은 기존 master 테이블에 억지로 컬럼을 붙이기보다 별도 테이블로 분리하는 방향을 우선 검토한다.
- master 직접 수정, alias 직접 수정, channel mapping 직접 수정은 기존 change request 원칙과 분리해서 다룬다.

## 3. 가격 관리 설계

가격은 최소 네 가지 층위로 나누어 관리하는 것이 좋다.

| 구분 | 설명 | 기준 |
|---|---|---|
| SKU별 매입가 | 사입 또는 제조 기준 원가. 마진 계산과 판매가 검토의 기준이 된다. | 내부 SKU |
| SKU별 기본 판매가 | 판매처별 변형 전의 기준 판매가. 내부 운영 기준 가격이다. | 내부 SKU |
| 옵션별 옵션가 | 같은 상품 안에서 옵션별로 달라지는 추가/차감 가격. | 내부 SKU 또는 옵션 SKU |
| 판매처별 판매가 | Smartstore, MakeShop, Ably, PlayAuto 등 각 판매처에 실제 노출하거나 업로드할 가격. | 내부 SKU + 판매처 |

SKU별 가격과 판매처별 가격은 분리해야 한다. 내부 기본 판매가는 하나라도 판매처 수수료, 배송비 포함 정책, 할인 정책, 판매처별 가격 제한 때문에 실제 업로드 가격은 달라질 수 있다.

기간별 가격 변경 가능성도 고려해야 한다. 예를 들어 특정 기간에만 판매가를 변경하거나, 원가 변경 이력을 남겨야 할 수 있다. 따라서 가격 후보 테이블에는 적용 시작일, 적용 종료일, 상태, 변경 사유, 작성자 같은 이력성 컬럼 후보를 둘 수 있다.

할인/프로모션 가격은 이번 v1 설계의 핵심 범위에서 분리한다. 추후 `promotion_price`, `channel_promotion_price` 같은 별도 구조로 확장할 수 있게 두고, 이번 단계에서는 기본 가격과 판매처별 업로드 가격의 기반만 잡는다.

## 4. 재고 관리 설계

재고도 실제 보유 재고와 판매처별 노출 재고를 분리해야 한다.

| 구분 | 설명 | 기준 |
|---|---|---|
| 실제 보유 재고 | 창고 또는 내부 운영 기준의 실재고. 피킹/출고 가능 수량의 기준이다. | 내부 SKU |
| 판매처별 노출 재고 | 각 판매처에 보여주거나 업로드할 재고. 실제 재고보다 작게 잡을 수 있다. | 내부 SKU + 판매처 |
| 안전재고 | 과판매 방지를 위해 판매처 노출에서 제외할 최소 보유 수량. | 내부 SKU 또는 판매처별 SKU |
| 품절 처리 기준 | 실제 재고, 안전재고, 판매처 정책을 조합해 품절 여부를 판단하는 기준. | 내부 SKU + 판매처 |

실제 재고와 판매처 노출 재고를 같은 값으로 취급하면 과판매 위험이 커진다. 여러 판매처에 같은 SKU를 동시에 노출하는 경우, 실제 재고 10개를 모든 판매처에 10개씩 노출하면 주문이 몰릴 때 문제가 생길 수 있다. 따라서 판매처별 노출 재고는 실제 재고에서 안전재고와 판매처 배분 정책을 반영한 값으로 분리한다.

채널별 재고 차감과 자동 동기화는 당장 구현하지 않는다. 이 기능은 주문 수집, 피킹 상태, 출고 확정, 취소/반품, 판매처 API 연동과 연결되므로 별도 단계에서 다룬다. 이번 설계에서는 export용 노출 재고를 계산하고 기록할 수 있는 기반만 잡는다.

## 5. 판매처별 Export 설계

판매처별 업로드 양식은 서로 다르다. 같은 내부 SKU라도 Smartstore, MakeShop, Ably, PlayAuto가 요구하는 필드명, 필수값, 코드 체계, 가격 필드, 재고 필드, 옵션 표현 방식이 다를 수 있다.

| 판매처 | 차이점 예시 |
|---|---|
| Smartstore | 상품번호, 옵션번호, 옵션가, 재고수량, 판매상태 등 판매처 고유 필드가 필요할 수 있다. |
| MakeShop | 상품 UID, 옵션 sto_id, 자체 옵션코드 등 기존 MakeShop 코드 연결이 중요하다. |
| Ably | 옵션/상품 업로드 양식, 판매가, 노출재고, 이미지 필드의 요구사항이 별도로 존재할 수 있다. |
| PlayAuto | 여러 판매처를 중계하는 구조라 원 판매처 코드와 PlayAuto 관리 코드가 함께 필요할 수 있다. |

따라서 export는 DB 데이터를 판매처별 업로드 양식으로 변환하는 별도 계층으로 본다. 내부 DB 컬럼명을 그대로 CSV/XLSX 컬럼명으로 쓰지 않고, 판매처별 template과 field mapping을 별도로 관리해야 한다.

별도 template과 field mapping이 필요한 이유는 다음과 같다.

- 판매처마다 필드명이 다르다.
- 같은 값도 판매처마다 다른 형식으로 변환될 수 있다.
- 필수값 누락 검증 기준이 판매처마다 다르다.
- 가격과 재고 필드가 판매처별로 분리되어야 한다.
- 후보 코드는 export 대상에서 제외하거나 별도 검수 상태로 표시해야 한다.
- 양식 버전이 바뀌어도 내부 master 구조를 바꾸지 않고 template만 갱신할 수 있어야 한다.

CSV와 XLSX export는 둘 다 고려한다. CSV는 자동 처리와 대량 업로드에 유리하고, XLSX는 판매처가 지정 양식을 제공하거나 사람이 검수해야 할 때 유리하다.

## 6. 추천 테이블 초안

아래 내용은 설계 후보이며 실제 DB 생성문이 아니다. 컬럼명도 확정이 아니라 후보 수준이다.

### `sku_price`

| 항목 | 내용 |
|---|---|
| 목적 | 내부 SKU 기준의 매입가, 기본 판매가, 옵션가를 관리한다. |
| 주요 컬럼 후보 | 내부 가격 ID, SKU ID, 매입가, 기본 판매가, 옵션가, 통화, 적용 시작일, 적용 종료일, 상태, 메모, 생성/수정 시각, 생성/수정자 |
| 연결 기준 | `sku_master.id`를 기준으로 연결한다. 상품 단위 기준 가격이 필요하면 `product_master.id`는 보조 참조로만 검토한다. |
| 주의점 | 판매처별 판매가를 여기에 섞지 않는다. 할인/프로모션 가격은 추후 별도 구조로 분리한다. 기간 중복과 활성 가격 2개 이상 발생을 막는 정책이 필요하다. |
| 기존 테이블과의 관계 | `sku_master`의 SKU 단위 가격 확장 테이블이다. `code_alias`, `sku_channel_mapping`의 코드 값과 직접 결합하지 않고 SKU ID를 통해 연결한다. |

### `sku_channel_price`

| 항목 | 내용 |
|---|---|
| 목적 | 판매처별 판매가, 옵션가, 판매처 노출 가격을 관리한다. |
| 주요 컬럼 후보 | 채널 가격 ID, SKU ID, 판매처 코드, 판매처 상품코드, 판매처 SKU/옵션코드, 판매가, 옵션가, 통화, 적용 시작일, 적용 종료일, 상태, 가격 산출 기준, 메모, 생성/수정 시각 |
| 연결 기준 | `sku_master.id`와 판매처 코드로 연결하고, 판매처 코드는 `sku_channel_mapping.channel_code`와 맞춘다. 판매처 옵션코드는 확정된 `sku_channel_mapping` 또는 확정 alias에서 가져온다. |
| 주의점 | 후보 channel code를 확정 판매처 가격에 바로 사용하지 않는다. 판매처별 가격이 내부 기본 판매가와 달라질 수 있음을 전제로 둔다. |
| 기존 테이블과의 관계 | `sku_channel_mapping`의 확정 판매처 연결을 기반으로 판매처별 가격을 붙인다. 내부 기본 가격은 `sku_price`에서 참조할 수 있다. |

### `sku_inventory`

| 항목 | 내용 |
|---|---|
| 목적 | 내부 SKU 기준의 실제 보유 재고와 안전재고를 관리한다. |
| 주요 컬럼 후보 | 재고 ID, SKU ID, 실제 재고수량, 가용 재고수량, 안전재고, 보류 재고, 재고 기준일시, 재고 출처, 상태, 메모, 생성/수정 시각 |
| 연결 기준 | `sku_master.id`를 기준으로 연결한다. 창고가 늘어날 경우 창고 코드 후보를 추가할 수 있다. |
| 주의점 | 판매처별 노출 재고와 섞지 않는다. 주문 차감, 피킹 확정, 반품 복귀 같은 재고 이동 원장은 추후 별도 단계로 분리한다. |
| 기존 테이블과의 관계 | `sku_master`의 재고 확장 테이블이다. export 시 `sku_channel_inventory`의 산출 기준이 될 수 있다. |

### `sku_channel_inventory`

| 항목 | 내용 |
|---|---|
| 목적 | 판매처별 노출 재고와 품절 기준을 관리한다. |
| 주요 컬럼 후보 | 채널 재고 ID, SKU ID, 판매처 코드, 판매처 상품코드, 판매처 SKU/옵션코드, 노출 재고수량, 안전재고 반영 여부, 품절 여부, 품절 기준, 적용 시작일, 적용 종료일, 상태, 메모, 생성/수정 시각 |
| 연결 기준 | `sku_master.id`와 판매처 코드로 연결한다. 판매처 코드와 옵션코드는 확정된 `sku_channel_mapping`을 우선 사용한다. |
| 주의점 | 실제 보유 재고와 동일하다고 가정하지 않는다. 판매처별 재고 배분 정책과 수동 조정값이 필요할 수 있다. |
| 기존 테이블과의 관계 | `sku_inventory`를 기반으로 판매처별 노출 재고를 만들고, `sku_channel_mapping`으로 판매처 업로드 대상 코드를 찾는다. |

### `channel_export_template`

| 항목 | 내용 |
|---|---|
| 목적 | 판매처별 CSV/XLSX 양식의 버전과 기본 정보를 관리한다. |
| 주요 컬럼 후보 | template ID, 판매처 코드, template 이름, template 버전, 파일 형식, 인코딩, 구분자, 헤더 포함 여부, 활성 여부, 설명, 생성/수정 시각 |
| 연결 기준 | 판매처 코드 기준으로 `sku_channel_mapping.channel_code`, `sku_channel_price`, `sku_channel_inventory`와 연결된다. |
| 주의점 | template은 판매처 양식 변화에 따라 버전 관리해야 한다. 내부 DB 구조 변경 없이 template 버전을 바꿀 수 있어야 한다. |
| 기존 테이블과의 관계 | 기존 master 데이터를 직접 바꾸지 않고 export 변환 계층에서 참조한다. |

### `channel_export_field_mapping`

| 항목 | 내용 |
|---|---|
| 목적 | 내부 데이터 필드를 판매처별 업로드 필드로 매핑한다. |
| 주요 컬럼 후보 | field mapping ID, template ID, 판매처 필드명, 내부 데이터 출처, 내부 필드 후보, 필수 여부, 기본값, 변환 규칙 설명, 정렬 순서, 활성 여부, 검증 메모 |
| 연결 기준 | `channel_export_template`의 template ID에 연결된다. 내부 출처는 `sku_master`, `product_master`, `code_alias`, `sku_channel_mapping`, `sku_price`, `sku_channel_price`, `sku_inventory`, `sku_channel_inventory`, `product_image` 중 하나로 문서화한다. |
| 주의점 | 변환 규칙을 실행 코드와 섞지 않고 문서/설정으로 관리할 수 있어야 한다. 후보 코드를 확정 코드처럼 내보내지 않도록 검증 규칙을 둔다. |
| 기존 테이블과의 관계 | 기존 테이블의 값을 판매처 필드로 변환하는 설명 계층이다. |

### `export_job`

| 항목 | 내용 |
|---|---|
| 목적 | 판매처별 내보내기 작업 단위와 실행 상태를 관리한다. |
| 주요 컬럼 후보 | export job ID, 판매처 코드, template ID, 요청자, 요청 시각, 대상 SKU 조건, 작업 상태, 총 대상 건수, 성공 건수, 실패 건수, 검증 오류 요약, 생성/완료 시각 |
| 연결 기준 | `channel_export_template`과 판매처 코드에 연결된다. 대상 SKU는 선택 조건 또는 별도 job item 후보 구조로 관리할 수 있다. |
| 주의점 | export 실행은 DB 변경과 분리한다. 파일 생성 실패, 필수값 누락, 후보 코드 포함 같은 검증 결과를 남겨야 한다. |
| 기존 테이블과의 관계 | 기존 상품/가격/재고 데이터를 읽어서 export 파일을 만드는 실행 이력이다. |

### `export_file_history`

| 항목 | 내용 |
|---|---|
| 목적 | 생성된 CSV/XLSX 파일의 이력, 파일 위치, 다운로드 상태를 관리한다. |
| 주요 컬럼 후보 | file history ID, export job ID, 파일명, 파일 형식, 파일 경로 또는 저장소 키, 파일 크기, 행 수, checksum 후보, 생성 시각, 만료 시각, 다운로드 횟수, 메모 |
| 연결 기준 | `export_job`의 작업 ID에 연결된다. |
| 주의점 | 파일에는 판매처 업로드용 민감 데이터가 포함될 수 있으므로 접근 권한과 보관 기간 정책이 필요하다. outputs/exports 폴더를 임의로 git에 추가하지 않는 운영 원칙도 유지해야 한다. |
| 기존 테이블과의 관계 | 기존 master와 직접 연결되기보다 export 작업의 결과 파일 이력을 기록한다. |

## 7. 판매처별 Export 처리 흐름

권장 흐름은 다음과 같다.

1. VSKU/SKU 선택
2. 판매처 코드 조회
3. 가격/재고 조회
4. 판매처별 양식 template 적용
5. CSV/XLSX 생성
6. export 이력 저장

각 단계별 참조 구조는 다음과 같다.

| 단계 | 참조 테이블/후보 테이블 | 설명 |
|---|---|---|
| VSKU/SKU 선택 | `sku_master`, `product_master`, `code_alias`, `product_code.v_sku_canonical` | 내부 기준 SKU를 선택한다. 화면에서는 selfpia SKU, VSKU, 상품명, 옵션명으로 검색할 수 있다. |
| 판매처 코드 조회 | `sku_channel_mapping`, `code_alias` | 판매처별 확정 상품코드와 옵션/SKU 코드를 찾는다. 후보 alias는 검수 표시용으로만 사용하고 확정 export에서는 제외한다. |
| 가격/재고 조회 | `sku_price`, `sku_channel_price`, `sku_inventory`, `sku_channel_inventory` | 내부 기본 가격/재고와 판매처별 판매가/노출재고를 분리해서 조회한다. 판매처별 값이 있으면 그 값을 우선하고, 없으면 fallback 정책을 별도로 정한다. |
| template 적용 | `channel_export_template`, `channel_export_field_mapping`, `product_image` | 판매처별 필드명, 필수값, 정렬 순서, 이미지 URL, 가격/재고 필드 변환 규칙을 적용한다. |
| CSV/XLSX 생성 | export service 계층 | DB row를 판매처 업로드 양식으로 변환한다. 이 단계는 DB master를 수정하지 않는다. |
| export 이력 저장 | `export_job`, `export_file_history` | 요청 조건, template 버전, 생성 파일, 검증 결과, 실패 사유를 남긴다. |

중요한 점은 export가 master 수정 기능이 아니라는 것이다. export는 확정된 내부 데이터와 판매처별 확장 데이터를 읽어 파일로 변환하는 계층이다. 판매처 코드 확정, 가격 승인, 재고 조정은 별도 workflow에서 다루고, export는 그 결과를 양식으로 만드는 역할을 맡는다.

## 8. 프론트 메뉴/화면 확장안

현재 프론트는 read-only 검수 화면 중심이다. 가격/재고/export도 처음에는 read-only 또는 draft 검수 중심으로 시작하는 것이 안전하다.

향후 메뉴 확장안은 다음과 같다.

| 메뉴 | 화면 | 초기 범위 |
|---|---|---|
| 상품 관리 > 가격 관리 | SKU별 매입가, 기본 판매가, 옵션가 조회 | read-only 목록/상세 |
| 상품 관리 > 재고 관리 | SKU별 실제 재고, 안전재고, 품절 기준 조회 | read-only 목록/상세 |
| 채널 관리 > 판매처별 가격/재고 | 판매처별 판매가와 노출재고 조회 | read-only 검수 |
| Export 관리 > 판매처별 내보내기 | 판매처, template, 대상 SKU 선택 후 dry-run 또는 파일 생성 | 초기에는 preview 중심 |
| Export 관리 > 내보내기 이력 | 생성된 파일, 건수, 오류, template 버전 확인 | read-only 이력 조회 |

프론트에서 가격이나 재고를 직접 수정하는 기능은 바로 넣지 않는다. 변경 요청/승인 흐름은 추후 단계로 분리한다. v1에서는 조회, 검수, 누락값 확인, export preview를 우선하고, 실제 수정/승인/반영은 change request 또는 별도 권한 체계가 준비된 후 도입한다.

## 9. 단계별 구현 순서

안전한 구현 순서는 다음과 같다.

1. 설계 문서 확정
2. 샘플 CSV/XLSX 양식 수집
3. 판매처별 필드 매핑표 문서화
4. 로컬 DB 전용 schema draft 작성
5. dry-run 검증 SQL 작성
6. API read-only 조회 추가
7. 프론트 read-only 화면 추가
8. export 파일 생성 기능 추가
9. 승인 후 운영 반영 검토

이번 작업에서는 1단계 문서 작성만 진행한다. 로컬 DB 전용 schema draft, dry-run 검증 SQL, API, 프론트, 파일 생성 기능은 이번 범위가 아니다.

## 11. 대표님 보고용 요약

1. 이번에는 DB를 건드리지 않고 가격/재고/판매처 업로드 양식 구조를 문서로 먼저 정리했습니다.
2. 기존 상품코드 구조는 유지하고, 가격/재고/export 기능은 별도 확장 구조로 잡는 방향입니다.
3. 나중에 프론트에서 가격이나 재고를 수정하면 스마트스토어/메이크샵/에이블리/플레이오토 양식으로 내보낼 수 있게 설계했습니다.
4. 아직 실제 반영이나 DB 변경은 하지 않았습니다.
5. 다음 단계는 판매처별 실제 업로드 양식을 모아서 필드 매핑표를 만드는 것입니다.
